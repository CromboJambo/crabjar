# ADR-001: Agent Execution Architecture

**Status:** Accepted  
**Date:** 2026-09-17  
**Context:** Derived from architectural reasoning about safe, observable agent execution on Unix systems. Establishes crabjar's core design principles.

## Problem

Agents (human or autonomous) need to execute actions on Unix machines with the following properties:
- Safe by default, powerful when needed
- Fully observable and accountable
- No forensic archaeology required to understand what happened
- Works across privilege boundaries without running everything as root

## Decision

Adopt a layered architecture with explicit trust boundaries and mandatory observability.

### 1. Privileged Helper Pattern

Large unprivileged controller communicates with tiny, narrowly-scoped privileged helpers:

```
agent (unprivileged)
    │
    ├── authenticated request
    ├── exact target device/path
    ├── exact operation
    └── result + timestamp
        │
privileged helper (root, minimal)
    │
    └── execute single operation
```

The privileged component performs exactly one operation and nothing else. It is not a daemon; it is invoked per-operation with explicit parameters.

### 2. Accountability Fabric Over Panopticon

Not an asymmetric observer watching subjects. All participants (human, agent, machine) can inspect each other's actions according to permissions:

```
┌──────────────┐
│    HUMAN     │
└──────┬───────┘
       │ observes / approves
┌──────▼───────┐    ┌──────────┐
│    AGENT     │◄──►│  LOGGER  │
└──────┬───────┘    └──────────┘
       │
┌──────▼───────┐
│   MACHINE    │
└──────────────┘
```

Every meaningful action leaves an inspectable trail. "What did the agent do?" is a query, not forensics.

### 3. External Observer Environment

For inspection/repair operations, use a fresh, known-good environment rather than operating inside the patient system:

- Container execution for isolation
- Live USB as "grown-up rubber duck" — external perspective on broken system
- Agent should not be inside the machine's normal userspace when making consequential decisions

### 4. Safe Remote Execution Chain

Replace `curl | bash` with an inspectable pipeline:

```
fetch → hash → inspect → diff → approve → execute → record
```

The forbidden spell is not made safe; it is replaced by a chain where each step is optional but inspectable.

### 5. Unix Game Mechanics

Unix already provides all necessary primitives: processes, files, permissions, pipes, signals, mounts, services, exit codes. The architecture's job is to make these legible and safe for humans and agents to use — not to invent new mechanics.

### 6. Culture Over Enforcement

Good practices should be propagated by making them natural and obvious, not by mandating compliance:

- **Gate, not fence** — guide behavior rather than constrain it
- **Pick up your toys when done** — leave the system cleaner than you found it
- **Don't leave crumbs or we'll get ants** — small messes attract bigger problems

The architecture should make good habits easy and bad habits visible, but not impossible. Trust participants to understand the why behind the patterns.

## Consequences

- **Positive:** No invisible mutation; full auditability; privilege escalation is explicit and bounded
- **Negative:** More moving parts than a simple `sudo` invocation; requires trust layer management
- **Trade-off:** Safety over convenience; observability over speed

- Unix game mechanics: processes, files, permissions, pipes, signals as primitives
