# ADR-008: Jev Cooperative Integrated Evolution Decision Architecture

**Status:** Accepted  
**Date:** 2026-10-17  
**Context:** Derived from Phase 1 implementation of the Jev decision layer (specs/jev-cooperative-integrated-evolution.md). Establishes crabjar's semantic decision-making architecture with persistent evidence store and learning loop.

## Problem

Agent decisions must evolve from adversarial rule-checking to cooperative, integrated evaluation that learns from outcomes. Requirements:
- Evaluate observations against criteria using embedding similarity (Jev/SemIf pattern)
- Track decision outcomes over time for continuous improvement
- Cache frequent decisions to reduce expensive embedding computation
- Support multi-method decision strategies with performance metrics
- Provide CLI surface for feedback, metrics, and rule promotion

## Decision

Implement a three-phase evolution architecture with persistent evidence store and learning loop.

### 1. Three Evolutionary Phases

```
Adversarial (complete) → Cooperative (Phase 1) → Integrated (future)
   Rule-checking            Embedding similarity      Multi-method ensemble
   Binary pass/fail         Confidence scoring        Adaptive method selection
```

**Phase 1 (Cooperative)** — Implemented in this ADR:
- Embedding-based semantic similarity matching
- Decision caching with TTL
- Outcome tracking and feedback loop
- Multi-method decision strategies

### 2. Architecture Overview

```
CLI (crabjar decide)
    │
    ├── evaluate → handle_evaluate()
    │   ├── Check cache (in-memory, 1000 entries, 24h TTL)
    │   ├── Query DB for prior similar observations
    │   ├── Compute embedding similarity
    │   └── Persist decision to SQLite evidence store
    │
    ├── feedback → handle_feedback()
    │   └── Record outcome (correct/incorrect) for observation hash
    │
    ├── metrics → handle_metrics()
    │   └── Time-filtered method performance statistics
    │
    ├── promote-rule → handle_promote_rule()
    │   └── Promote high-confidence decision to permanent rule
    │
    └── learnings → handle_learnings()
        └── Query decisions by component for analysis
```

### 3. Evidence Store Design

**Technology:** SQLite via rusqlite (version-agnostic manual `.next()` iteration)

**Schema:** `decisions` table with columns:
- `id` — auto-increment primary key
- `observation_hash` — SHA256 hash of observation text
- `method` — decision method used (e.g., "embedding", "rule")
- `confidence` — similarity score (0.0–1.0)
- `outcome` — user feedback ("correct", "incorrect", or null)
- `component` — system component affected by decision
- `decision_data` — JSON payload with full decision context
- `created_at` — Unix epoch timestamp

**Key methods:**
- `recent_decisions(limit)` — retrieve recent decisions for analysis
- `method_stats()` — aggregate statistics by decision method
- `method_stats_since(since_epoch)` — time-filtered method statistics
- `get_decision_by_id(id)` — lookup specific decision for promotion

### 4. Learning Loop Integration

The learning loop operates in three stages:

1. **Cache Check:** Before expensive embedding computation, check if a similar observation was previously evaluated and marked "correct". If so, return the cached decision immediately.

2. **Decision Execution:** Compute embedding similarity against criteria file, generate confidence score, and persist to evidence store.

3. **Feedback Collection:** User provides outcome via `crabjar decide feedback --obs-hash <hash> --outcome correct|incorrect`. This trains the system for future similar observations.

**Cache Strategy:**
- In-memory LRU cache (1000 entries)
- 24-hour TTL
- Keyed by observation hash
- Only caches decisions marked "correct"

### 5. CLI Interface

```bash
# Evaluate observation against criteria
crabjar decide evaluate --observation "<text>" --criteria-file <file> [--backend hash|embedding] [--threshold 0.3] [--fresh]

# Provide feedback on decision outcome
crabjar decide feedback --obs-hash <hash> --outcome correct|incorrect

# View decision metrics (time-filtered)
crabjar decide metrics [--last 24h|7d|all]

# Promote high-confidence decision to permanent rule
crabjar decide promote-rule --decision-id <id>

# Query decisions by component for learning analysis
crabjar decide learnings --component <name>

# List available criteria files
crabjar decide list-criteria [--search-path <path>]

# Validate criteria file format
crabjar decide validate --criteria-file <file>
```

### 6. Method Performance Tracking

The system tracks per-method statistics:
- Total decisions made
- Correct vs incorrect outcomes (from feedback)
- Average confidence score
- Time window filtering (24h, 7d, all-time)

This enables adaptive method selection in future phases — promoting methods with higher accuracy for specific decision types.

## Consequences

- **Positive:** Decisions improve over time through feedback loop; expensive embedding computation is cached and avoided for repeated observations; full audit trail of decisions and outcomes
- **Negative:** Added complexity in decision pipeline; requires user feedback to be effective (cold start problem)
- **Trade-off:** Learning capability vs initial decision latency (first evaluation of new observation type is slower)

## Implementation Details

**Files modified/created:**
- `src/lib.rs` — CLI enum with decide subcommands and arguments
- `src/main.rs` — Command dispatch for all decide subcommands
- `src/commands/semantic.rs` — Semantic decision handlers (evaluate, feedback, metrics, promote-rule, learnings)
- `src/commands/decide_db.rs` — SQLite evidence store implementation

**SQLite iteration fix:** rusqlite 0.37's `Rows` type does not implement the `Iterator` trait. Used manual `.next()` loop pattern for version-agnostic compatibility:
```rust
loop {
    let row = match rows.next() {
        Ok(Some(r)) => r,
        Ok(None) => break,
        Err(e) => return Err(...),
    };
    // process row
}
```

**Column index alignment:** SELECT returns 10 columns (indices 0-9); code must read indices 0-9 to match column order in query.
