# Dynamic Component Loading via Wasmtime Embedding

## Problem Statement

Crabjar currently loads components statically at compile time. This limits:
- Hot reloading of agent behavior without process restart
- Dynamic plugin discovery and loading at runtime
- Sandboxed execution of untrusted or community-contributed components
- Fine-grained lifecycle management (activate/deactivate individual components)

## Solution Architecture

Embed the Wasmtime WebAssembly runtime to enable dynamic component loading:

```
Crabjar Host (Rust)
├── Component Loader (Wasmtime Engine)
│   ├── Load .wasm binaries from disk/network
│   ├── Instantiate components with capability-mediated imports
│   └── Manage component lifecycle (activate/deactivate/teardown)
├── DAGR Event Bus (existing)
├── Session Persistence (existing)
└── Agent Orchestration (existing)
```

## Component Interface Design

Define component interface via WebAssembly Interface Types (WIT):

```wit
define plugin {
    // Lifecycle
    activate: func(config: string) -> result<null, string>;
    deactivate: func() -> result<null, string>;

    // Event handling
    handle_event: func(event_type: string, payload: string) -> result<string, string>;

    // State management (for revertible effects)
    snapshot_state: func() -> result<string, string>;
    restore_state: func(state: string) -> result<null, string>;
}
```

## Implementation Phases

### Phase 1: Wasmtime Integration Foundation
- Add `wasmtime` and `wasmtime-component` crates to dependencies
- Create `crabjar-wasm` crate for component loading infrastructure
- Implement basic component instantiation with empty imports
- Test: Load a trivial "hello world" WebAssembly module

### Phase 2: Component Interface & Bindings
- Define WIT interface file for crabjar components
- Generate Rust bindings using `wasmtime::component::bindgen!`
- Implement capability-mediated host imports (event bus access, state persistence)
- Test: Load component and call lifecycle methods through bindings

### Phase 3: Dynamic Loading & Hot Reloading
- Implement component loader that discovers .wasm files in configurable directories
- Add runtime API for loading/unloading components by name
- Implement hot reload: instantiate new component, migrate state, drop old instance
- Test: Load component, modify behavior, reload without host restart

### Phase 4: Sandboxing & Security
- Configure Wasmtime store limits (memory, instruction count)
- Implement capability-mediated imports for all side effects
- Add import/export validation against declared interface
- Test: Verify sandbox boundaries (memory overflow, unauthorized imports)

### Phase 5: Integration with Existing Systems
- Wire component event handling to DAGR event bus
- Integrate snapshot/restore with session persistence layer
- Add component lifecycle management to conductor API
- Test: End-to-end flow from component load to event processing to state persistence

## Testing Strategy

1. **Unit tests**: Wasmtime engine initialization, module loading, binding generation
2. **Integration tests**: Component lifecycle (activate → handle events → deactivate)
3. **Hot reload tests**: State migration during component replacement
4. **Sandbox tests**: Memory limits, import/export validation
5. **Performance benchmarks**: Load time, instantiation time, call overhead vs native

## Integration Points

- **DAGR Event Bus**: Components register for event types, receive events through `handle_event`
- **Session Persistence**: Component state snapshots integrated with existing persistence layer
- **Conductor API**: New endpoints for component management (list, load, unload, reload)
- **Guard System**: Components can be gated by approval flows before loading

## Acceptance Criteria

1. Host process can dynamically load .wasm components at runtime without restart
2. Components can be unloaded and reloaded with state preservation
3. Component side effects are mediated through host imports (sandboxed)
4. Component lifecycle is managed through conductor API
5. Performance overhead is measured and documented (< 10% call overhead target)
